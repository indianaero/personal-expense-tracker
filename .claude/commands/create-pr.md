You are helping create a professional GitHub pull request to merge a feature branch into `main`.

The user invoked this command with: $ARGUMENTS

Parse $ARGUMENTS as follows:
- First token (may be a branch-style name like `feature/expense-crud` or a plain word) → **feature name**
- Everything after the first token, optionally quoted → **short summary**

If either value is missing or $ARGUMENTS is empty, tell the user the expected usage and stop:
> Usage: /create-pr <feature-name> "<short summary>"
> Example: /create-pr feature/expense-crud "Add secure expense CRUD feature"

---

## Step 1 — Analyse the repository

Run the following commands and collect their output before doing anything else. Do NOT skip any of them.

1. `git status` — working tree state
2. `git branch --show-current` — current branch name
3. `git log main..HEAD --oneline` — commits on this branch not yet in main
4. `git diff main...HEAD --stat` — files changed vs main
5. `git diff main...HEAD` — full diff vs main (read carefully — this drives the description)

If `git log main..HEAD --oneline` returns no commits, warn the user:
> This branch has no commits ahead of main. There is nothing to merge.
> Ensure you are on the correct feature branch before running /create-pr.

Then stop.

---

## Step 2 — Draft the pull request

Using the git output from Step 1, draft the following. Do NOT present any files or ask any questions yet — produce the full draft silently and move to Step 3.

### Draft elements

**PR title** (≤ 72 characters)
- Format: `<type>: <imperative summary>`
- Types: `feat`, `fix`, `refactor`, `docs`, `chore`, `test`
- Derived from the commits and diff, cross-referenced with the user's summary
- Example: `feat: add secure CRUD operations for user expenses`

**Base branch:** `main`
**Compare branch:** current branch from `git branch --show-current`

**PR body** using this exact structure:

```
## Summary
<!-- 2–4 bullet points describing WHAT was built and WHY -->

## Changes
<!-- Grouped list of files changed, with a one-line description per group -->

## How to test
<!-- Step-by-step checklist a reviewer can follow to verify the feature works -->

## Notes
<!-- Breaking changes, migration steps, known limitations, follow-up issues — omit section if none -->
```

Rules for the body:
- Summary bullets describe user-facing behaviour, not implementation details
- Changes section groups related files (e.g. "API routes", "UI components", "Service layer") — do not list every file individually
- "How to test" must be actionable: numbered steps, not vague ("test the feature")
- Use plain GitHub Markdown only — no HTML, no emoji unless the repo already uses them

---

## Step 3 — Present the draft for approval

Show the user exactly what will be written, formatted as a code block so they can review it precisely. Then ask:

> Does this look right? Reply **yes** to generate the PR file, or tell me what to change.

Wait for the user's response. Do not proceed until you receive explicit confirmation.

- If they say **yes** / **looks good** / **go ahead** / **approved** → proceed to Step 4
- If they request changes → revise the draft, re-present it, and ask again
- If they say **no** / **cancel** / **stop** → acknowledge and stop

---

## Step 4 — Generate the PR file

Only after receiving explicit approval, create the file:

**Path:** `docs/pull-requests/<feature-name>-pr.md`

Where `<feature-name>` is the first argument with any `/` replaced by `-` (e.g. `feature/expense-crud` → `feature-expense-crud`).

File format:

```markdown
---
title: "<approved PR title>"
base: main
compare: <current branch>
date: <today's date as YYYY-MM-DD>
---

<approved PR body — exactly as confirmed>

---
*Generated by /create-pr on <today's date>*
```

After writing the file, print a brief confirmation:

> PR file created at `docs/pull-requests/<feature-name>-pr.md`
>
> To open the pull request on GitHub, run:
> ```
> gh pr create --base main --head <current-branch> --title "<title>" --body-file docs/pull-requests/<feature-name>-pr.md
> ```

Do not run `gh pr create` automatically. The user decides when to open the PR.
